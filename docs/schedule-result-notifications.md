# 计划任务结果通知

Mac 和 iPhone 的计划任务新增/编辑表单，在「跑完自动归档」下面提供「通知任务结果」。默认关闭，已有任务不会自动开启。设置保存在执行主机，换设备编辑同一任务时读取同一份设置。

开启后，每次运行结束会向已登记的手机推送结果摘要或失败原因，包括创建会话之前发生的失败。自动归档不影响通知。点击通知打开该主机上该任务的运行记录，不依赖会话仍在侧栏中，也不提供会话回复/批准按钮。

## Bark 接入（无需 Apple 开发者密钥）

1. 在 iPhone 安装 App Store 版 Bark，允许通知并开启锁屏显示。
2. 在任务执行主机安装并启用新版 `live-activity` 插件。
3. 在 Paseo「设置 → Bark 通知 → 配置 Bark 推送…」选择执行主机，粘贴 Bark 首页的 HTTPS 推送地址并保存。计划任务编辑页也有同一配置入口。
4. 点「发送 Bark 测试通知」，确认手机收到后，打开任务的「通知任务结果」并保存。

配置按执行主机共享，Mac 和 iPhone 都可管理。地址可以是 `https://api.day.app/<device-key>`，也可以是 Bark 首页带示例标题/正文的测试链接；示例内容及查询参数不会带入实际请求。当前支持根路径部署的 HTTPS Bark 服务。

设备密钥只保存在执行主机的 `live-activity/bark.json`（0600），不回传给客户端，也不写入普通插件设置。实际推送使用 `POST /push`，密钥放在请求体内。默认向配置的 Bark 服务发送任务名称和结果摘要，系统通知归属于 Bark。此通道不提供灵动岛更新或通知中的回复/批准操作。

配置 Bark 后，任务结果优先走 Bark，不同时经 APNs 重复通知。移除 Bark 配置后恢复使用主机上原有的 APNs 目标；没有任何可用目标时，新的任务通知开关不可开启。实时活动的 APNs 行为不变。更换 Bark 目标不会将配置之前的任务历史发给新目标。

### 普通会话完成通知

在同一 Bark 设置中开启「会话完成通知」，即可把该主机普通会话每次回复完成的标题和回复摘要推送到手机。默认关闭，已有配置也不会自动开启。Mac 正在使用时仍会推送，Mac 原来的系统通知照常保留。点击 Bark 通知通过 `paseonative://agent/<serverId>/<agentId>` 打开对应会话。

此开关与各计划任务的「通知任务结果」独立；计划任务会话和子会话会被排除，避免额外通知。不会补发开启前的完成记录，也不会将权限请求或报错当作完成推送。同一完成事件去重，后续回合可再次通知。会话完成为实时、尽力发送，不使用计划任务的持久化重试机制。

开启时，会话完成改走 Bark，避免同时经 APNs 重复推送；关闭时恢复原有 APNs 判断。更换 Bark 地址后需重新开启，保存同一地址则保留设置。配置界面可在 Mac 和 iPhone 管理同一开关。

## 使用条件

- 执行任务的主机需要安装并启用支持 `schedule.notifications.read/write` 的新版 `live-activity` 插件。
- 配置上面的 Bark 通道，或者完成原生 APNs 配置。后者要求 iPhone「设置 → 通知 → 灵动岛推送」所选推送主机是这台执行主机，并完成密钥配置、设备令牌登记及系统通知授权。见 [README 的推送说明](../README.md#灵动岛和推送可选需要付费开发者账号)。
- 当前结果监测读取插件所在主机的运行记录，不覆盖其他关联主机的计划任务。普通会话的跨主机汇总推送保持原有行为。
- 表单会检查推送是否就绪；插件缺失、版本不支持或未配置手机推送时，显示说明，不能假装成功开启。已有通知开关在暂时没有可用手机时仍可关闭。

## 行为与边界

- 插件每 15 秒检查一次持久化运行记录，启动后无需等手机回到前台。开启之前已完成的任务不会补发；关闭期间完成的任务也不会在重新开启后补发。
- 单独按任务、运行和设备记录发送结果。重复检查及正常重启不重复发送；发送失败按退避策略重试，只处理仍在运行历史中且结束不超过 24 小时的记录。
- 这是单独的显式订阅，即使 Mac 正在使用也会向手机推送任务结果。前台 iPhone 不会把它误判为已有本地通知而隐藏。
- 主机停机、调度服务未运行或没有留下运行记录的漏执行，无法由同一台主机及时告警。本功能不虚构失败运行；主机无法访问 Bark / Apple 推送服务期间只能等待恢复后重试。
- 任务和通知设置使用两个独立的保存请求。通知保存失败会明确显示「任务已保存，但通知设置未保存」；在同一表单重试会沿用已创建的任务，避免重复创建定时任务。多设备并发修改通知设置使用 revision 检查。

## 实现与验证

Bark 配置页由设置页的导航容器统一弹出，不能把弹窗挂在 `Form` 内的 `Section` 上；后者在 iOS 会产生重复呈现并意外关闭。`MobileTests/BarkPresentationTests.swift` 覆盖反复打开、状态读取失败、表单刷新/滚动后仍保留配置页，以及关闭 Bark 后留在上一级设置页。

官方 `ScheduleTarget.config` 会丢弃不认识的字段，因此不向 `schedule/create` 或 `schedule/update` 塞入未支持的通知属性。App 使用 `plugin.rpc.invoke.request` 调用 `live-activity`：

| 方法 | 输入 | 输出 |
| --- | --- | --- |
| `schedule.notifications.read` | `scheduleId?`，新增表单省略 | `version: 1, enabled, revision, ready` |
| `schedule.notifications.write` | `scheduleId, enabled, expectedRevision` | 同上 |
| `bark.status` | 空对象 | `configured, serverURL, notifyOnFinish, lastPush`（不含设备密钥） |
| `bark.configure` | `pushURL` | 同上 |
| `bark.preferences` | `notifyOnFinish` | 同上 |
| `bark.clear` | 空对象 | 同上 |
| `bark.test` | 空对象 | `at, ok, status, reason`（已脱敏） |

插件独立保存设置及发送记录，只读 daemon 的 `schedules/<id>.json`。结果通知使用 category `paseo.schedule-result`，携带 `reason: schedule_result`、`serverId`、`scheduleId`、`runId`，可选 `agentId`。

Bark 任务结果通知附带 `paseonative://schedule?serverId=…&scheduleId=…`，与 APNs 一样只打开任务历史，不触发任务执行。无需已存在的会话。App 忽略缺失、重复或非法的路由参数。

自动化验证涵盖协议解码、无会话的失败通知路由、成功/失败结果、自动归档、开关持久化、历史隔离、多设备去重、重启、断网重试和并发修改。Bark 额外覆盖配置权限、密钥不回显、HTTP/API 错误、发送标识去重，以及无 APNs 凭证的就绪判断。HTTP 200 且 Bark 响应 `code: 200` 仅代表服务接受，手机送达和点击跳转仍需真机确认。

2026-11-10 真机验收：Bark 连接测试通知已在锁屏收到；随后手动触发真实计划任务，运行成功，插件记录一次成功发送，用户确认收到结果通知且点击可进入对应任务记录。失败路径已通过模拟运行记录和失败传输的自动化测试，未人为破坏实际任务来制造失败。
